* Jon: One of the things we struggle with with that approach is that OS-level heuristics (for example) are sometimes less consistent than our approach . So a different balance of security vs. convenience. But would potentially undermine our ability to deliver a consistent or custom experience  
* Jon: Had instances where we had to work around poor browser/OS level heuristics. Relying on a 3P from our perspective makes it difficult to ensure the UX. We can work cooperatively, and use fallbacks.  
* Simeon: Main hesitation in the WECG. It’s not clear that asking the browser to take over the autofill functionality is the right approach  
* Rene: That’s been a contentious topic for a few years now. The push for having more of the autofill in the OS, while interesting, does present challenges when heuristics are involved. However, when there’s something that isn’t heuristic based (dedicated API call), it tends to go well with the OS-level APIs (barring bugs or lack of support). That’s the point where it ends up being more contentious. Where extensions will fall back to monkeypatching those APIs rather than going into OS integration. That’s where the friction lies. On our side, we’re also not very keen on letting go of our heuristics.  
* Jon: Wonder if it makes sense for our charter to not necessarily constrain ourselves to not considering the full ecosystem, as it will have context that informs web standards. Allow for out of scope conversation in the agenda.   
* Cathy: I’m in the unique situation at Meta where we built an entire browser out of WebView. So far we’re talking about extensions, but we’re WebView Android. We have additional data that users are interested in. We try to suppress system level autofill in order to present our own data. At the system level, there’s only one autofill provider: can’t provide an additional data source unless we want to take the entire thing over. My hope is to be able to evolve the system APIs so we can provide an additional data source so we can present data using the system provider. In terms of charter, I feel extensions are interesting.  
* Jon: We have devs working on similar situations adjacent to extensions as well. Agree that talking about extension APIs is only useful as additional context and use case.  
* Rene: Building off that, while I understand platform APIs are proprietary, providing feedback as a group is useful. Whatever we take into consideration to create a spec, those are the only APIs the web will have to interact with the page. * Yoav: To be clear, are we talking about webviews in native apps or integrating with native content?

* Jon: Seems like we see that there are ways to solve this from the host platform side (e.g. extension, OS app, mobile app, etc), what we’re trying to drive at is what are the commonalities that we can address from the page side. I’m curious, what are the issues folks are encountering on ecommerce sites or similar? What’s holding back those experiences from functioning properly?  
* Yoav: To a large extent this was discussed in the previous session. A lot of what goes wrong today is related to the complexities of data collection. One has to hope that autofill refills parts of a form that were added. Inserting hidden fields to capture data and move them around appropriately to match what the user is seeing. That’s what I’m aiming to tackle with the autofill API. There are other issues that would be great to discuss here. Going back to previous discussion, types of use cases autofill providers may want to tackle. One use case is to provide data. They want to provide data to autofill that allow the native heuristics to kick in and provide a good user experience with the right data. The other side is that the autofill provider has better heuristics and wants to present data from the autofill provider or the OS. Which one is closer to reality?  
* Jon: Users have already made a choice about how they’d like their secrets stored/handled; there’s a reason why they use non-system options. We see this (native handling) as additive (to our own). Being able to have multiple options means tuning to user preference. Our goal is to safely and conveniently get sensitive data from point A to B.  
* Yoav: Makes sense. If we build APIs on that front, they wouldn’t be web exposed APIs. Could be privileged UI APIs. We would need to influence multiple ecosystems to move in that direction.  
* Jon: My view is that defining signals that are useful from all of these different interacting concerns is the domain we can help with.   
* Yoav: Right, reduce heuristics on one hand. Browsers don’t like to let go of control. E.g. autofill shouldn’t be an option here. No standard way to set that beyond the autofill attribute, but that’s not a bullet proof signal. Could be useful to clearly state that this is something we want to help with.  
* Simeon: part of why I was floating the address book provider use case. We can’t dictate what other platforms do, but can identify related scenarios and clarify multi-party participation  
* … Then mobile platforms can take it or leave it  
* Jon: Who owns what concerns? Both page owner and a credential provider serve the user, but may be adversarial against one another. “You can’t autofill here” goes against the user’s desire  
* … The page can’t say don’t do this  
* Yoav: At the same time, that belongs in its own full discussion and the relevant folks aren’t necessarily here. There are cases where the browser heuristics are clearly wrong. An example from Shopify is a pickup location address, which is server provided. But it’s picked up as an address field, which causes the browser to shadow the UI that the site wants to provide. A case where the content wants to tell the provider “this isn’t what you think it is”. If we could define this in a non-adveserial way, that would be ideal, but we should follow up on this later.  
* Jon: Right, there are times where the heuristic strategies fail and page owners want to say “turn autofill off”, but  the real issue is that we don’t have enough context to make successful decisions (e.g. “address” is too ambiguous). We need more context and granularity. That’s the kind of discussion where we could be really productive in a larger conversation.
