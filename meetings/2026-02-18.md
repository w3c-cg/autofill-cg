* \[Yoav\] What are we trying to achieve here  
  * Create a "safe space" to talk about Autofill troubles, allow us to discuss the hacky things we have to do as browsers, web developers, and as Autofill providers  
  * There are some proposals that I am actively pursuing, and some that I think would be interesting to pursue.  
    * We're working on Autofill event proposal ([https://github.com/WICG/autofill-event](https://github.com/WICG/autofill-event)), give the web developer a chance to react to the autofill happening and to mutate form/etc. Currently test implementation in Chrome. Hope to discuss in the future.  
  * Other things that may be interesting:  
    * Marking up browser events (e.g., focus) as 'Autofill related', to avoid needing heuristical signals via CSS pseudo classes/etc.  
    * Autofill testability, how to automatically test Autofill as part of web-platform-tests (ideally), which requires it to be supported in browser automation APIs.  
      * Build an Autofill test suite that would let Autofill extensions  
    * Christoph also has a proposal relating to Autofill in iframes \+ permission policy ([https://github.com/explainers-by-googlers/safe-text-input/](https://github.com/explainers-by-googlers/safe-text-input/)), how to tell the autofill provider that it's safe to fill across origin boundaries (e.g., from a main-frame triggered fill into a cross-origin iframe)  
    * Yoav: There's also the same-origin case, where we still have multiple forms in each iframe (though it's a single field) for UI purposes, and this feels like something we can maybe resolve in other ways.  
      * (Something about CSS)  
      * (In chat, Jon Prusik: see also closed shadow roots)  
  * Yoav: Other proposals/thoughts?  
    * Christoph: Autofilling elements that are not input, select, or text area. For example custom selects built with DIVs/etc, they're difficult as an Autofill provider.  
      * \<selectmenu\> is maybe helping here, but unclear  
      * Brandon: Yeah at 1Password we ignore those fake elements and look for hidden selects, which works most of the time but definitely not.  
  * Brandon: For the previous proposals \+ web extensions in general. Have we thought how we can involve the Web Extension CG?  
    * Yoav: We can definitely do that, I haven't thought about it. Would also be great just to hear from yourselves in future discussions on these proposals, to get extension perspective and that feedback.  
      * We want Autofill to work well for our users no matter what the browser or Autofill provider is.  
    * Jon: Having some ability for extensions to behave in a space where the host page also doesn't have access to would be very useful. Today we have to operate in the host page space, so malicious script/etc or just an antagonistic page can be very difficult for us.  
      * Extensions have permission models, but users \[missed this\] for autofill extensions.  
      * Think we need some path to a user-directed privilege execution.  
      * Yoav: So you're talking about different APIs to let extensions interact with autofill in some way?  
      * Jon: Yes, but I don't see them as mutually exclusive to the current things you're proposing. I assume the web developer is often trying to protect against automated scripts, and we're saying "no, the user directed this".  
    * David: Possibly more of a question for the \[missed this\], I suspect Autofill is not the only use case for having a privileged space for   
    * Stephen: From a browser perspective, I’m not at all familiar with the challenges y’all face for extension-based Autofill, and it’d be great to just hear about that \- sites fighting you over autofill may be different from sites fighting browsers over autofill  
    * Rene \- RE privileged UI, there’s a proposal in the WICG related to clickjacking, to have some way to get privileged UI. Would be important for this group to discuss as well and to collaborate with WICG on  
    * Brandon \- Glancing through the autofill event proposal it seems focused on a single frame, where extensions need to coordinate across frames. A web extension API that gives the extension the data for all frames could help  
      * Also, content-editable divs.   
      * Also, autocomplete=off (or autocomplete=garbage, etc), a lot of websites misuse it, and we end up ignoring it.   
      * Also people using different field types, like search fields, text fields for passwords, etc.  
      * So not always "fighting" the site, but often things that may be just on accident or just slight misaligned  
    * David \- One trouble for passwords is \[validation\], how to trigger the website to actually run their validation  
      * We send all sorts of keyboard events, and waits to try and trick them into running their valdiation  
    * Jon \- closed shadow roots are also difficult, prevent us from seeing whats inside the shadow dom. Have to explicitly open them.  
      * Would be good to have quicker ways to know there's nested login three deep.  
      * Yoav: That would be completely extension focused API then?  
      * Jon: Maybe? Just thinking about it off the cuff. Maybe website can easily signal where autofill concerns are, because semantics alone don't work for nested shadow roots. Some sort of map?  
    * Stephen: about validation, we see that outside of just passwords \- also see it for address, for credit cards. Websites try to validate and get it wrong when autofill operated  
    * David: Some websites like to present things in web forms in multiple steps. One page for user name and another for passwords. Would be nice to have a way to connect those dots  
      * Also wanted to clarify expectations \- don’t expect that we’d get enough adoption in medium term to get rid of all the hacks. But ideally we can create an easier path  
    * Rene: For certain autofill things we have to monkeypatch some APIs, which ruffles some feathers. Provide a better way to provide credentials and autofilled things (under a dedicated extension API) could be interesting  
    * Jon: Core to that and to the autocomplete issue \- it conflates developer wishes and user wishes. For autofill providers our job is to follow the user’s wishes. Understanding why that is is also something we’re running into  
      * Some orgs don’t want users to use autofill on a certain portal. Tricky balance  
      * Yoav: Any idea how we can find more data? I doubt developers are doing this for fun, so… yeah, gathering more actual data would be great.  
      * Brandon: I don't have suggestions on getting data, just thought the bank one is interesting since its the biggest single source of problems for a website type for us. They really fight us on passwords.  
        * But it can also be ambiguous, for a lot of banks your username is your credit card. So the username is cc-number, and then we have to know that actually we're in a login form.
